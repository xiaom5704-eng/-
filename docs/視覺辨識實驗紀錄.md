# 藥錠照片檢索：開發實驗紀錄

日期：2026-09-20。正式服務仍使用現有 DINOv2 向量索引；以下未通過完整驗證的模型沒有接入正式搜尋，也沒有納入桌面安裝資料。

最新補充：2026-09-29 在新增的五款醫院公開照片上，未修改的正式服務前八名命中為 0／5；已另外驗證刻字查詢及一款實際 OCR／人工核對流程。見[醫院照片驗證](醫院照片驗證.md)，不能以人工查得取代圖片辨識驗收。

## 已確認的問題

使用者提供資料夾中的 Somin、K.B.T、Fencaine 照片，在正式模型的前八個候選中未找到預期品項。資料夾名稱只是開發測試的預期標籤，沒有完成獨立臨床核對。查詢照片從未寫入參考圖庫。

既有鏡像將 Fencaine 官方 5496×3670 圖片縮為 640×427。藥錠在原圖中佔比很小，再將整張圖縮為模型輸入時，刻字與輪廓容易流失。這是可觀察的資料品質問題，不代表只提高解析度就能完成自動辨識。

## 方法比較

| 方法 | 觀察 | 目前決定 |
| --- | --- | --- |
| 邊界背景顏色裁切 | 先前完整圖庫實驗沒有改善三張案例；參考圖變形測試也退步 | 不採用 |
| U2Netp 通用前景分割 | 可能把尺規當前景、合併兩顆藥錠，或移除重要細節；結果不穩定 | 不採用 |
| DEIMv2 藥錠偵測 | 六張圖片可找出藥錠，但也把藍色背景當物件；本機推論約 7–14 秒／張 | 暫未採用 |
| YOLO11n 藥錠定位＋DINOv2 裁切特徵 | 131 筆小圖庫排名為 1、3、1；擴至正式服務相同的 6,142 筆參考圖後為 22、97、2 | 仍有兩項不在前八名，未採用；授權與來源亦待釐清 |

| --- | ---: | ---: | ---: |
| Somin | 2370 | 124 | 22 |

## 已接入的獨立改善

官方參考圖下載與放大對照已接入搜尋、外觀查詢、CV 候選及藥品報告。保存來源、字號、時間、解析度及原始／衍生圖雜湊；不會將使用者查詢照片收入圖庫。操作與資料位置見[圖片功能說明](vision.md)。這個改善供人工核對，正式 CV 排名與相似度門檻未因而改變。

## 2026-09-22：局部特徵與選用外觀讀取

在隔離 Python 套件目錄以 OpenCV 4.13.0.92 測試 RootSIFT、比例篩選與 RANSAC；重用先前藥錠區域作開發比較。即使只比正確品項的官方參考圖，Somin、K.B.T 都沒有穩定幾何配對，Fencaine 僅 5 個內點且覆蓋範圍小，因此沒有用它取代正式檢索。實驗和結果在 `test-results/vision-detail-evaluation/sift-pilot.py`、`sift-pilot.json`，沒有新增正式依賴。

另一個方向是由開發機已安裝的 `qwen3.5:4b` 讀取外觀，將文字交給既有的嚴格本機搜尋。模型只收到照片與一般特徵任務，未收到預期品項、藥名、檔名或來源標籤。初次正式提示將三張照片都判為不確定；澄清「同一種藥的正反面可以分析」並讓影像與觀察指令放在同一訊息後，正式 API 得到以下結果：

| 照片的開發預期 | 模型可用輸出 | 本機候選 | 正式 API 耗時 |
| --- | --- | --- | --- |
| Somin | 圓形、粉、C | 永信舒敏錠，027569 | 約 31 秒 |
| K.B.T | SK KBT；形狀／顏色不確定留空 | 克瀉寧錠，007592 | 約 54 秒 |
| Fencaine | 圓形、FC 10；顏色不確定留空 | 優生芬康胃錠，031990 | 約 38 秒 |

每項當次搜尋有一筆候選，但仍不能當成照片身分已確認。這三張照片已用於開發與提示修正，不是獨立測試集；K.B.T 照片還含背景文字，不能單憑這次結果證明模型讀的是藥錠表面。初步結果與正式提示結果均保存，沒有把測試照片加入圖庫。證據為同目錄的 `local-vision-pilot.json`、`production-observer-before-prompt-fix.json`、`production-observer-results.json`。

正式接入為**選用的外觀欄位預填**：先顯示可修正欄位，必須按核對搜尋才查資料庫；不自動確認藥品、不產生醫療結論、不改 DINOv2 排名與門檻。一般 CV／OCR 照常獨立運作，模型不可用時不自動切換 Gemini。功能細節見 [圖片功能說明](vision.md)。整體照片辨識準確率仍未驗證。

## 2026-09-22：照片模式的完整刻字漏查

正式 API 複現：三張開發照片分別輸入 C、SK KBT、FC 10，原流程皆未在前八名出現預期品項。原因是先以圖片門檻篩選，刻字僅用於通過門檻後的排序。修正後，完整刻字另查全部本機外觀資料，再與圖片候選合併；圖片門檻、參考向量、查詢照片均未改動。

| 開發照片／人工刻字 | 修正後結果 | 證據種類 |
| --- | --- | --- |
| K.B.T／SK KBT | 一個刻字符合品項，克瀉寧列第一；图片相似度約 0.495 | 刻字相符，照片未達門檻 |
| Fencaine／FC 10 | 一個刻字符合品項，芬康胃列第一；圖片相似度約 0.352 | 刻字相符，照片未達門檻 |
| Somin／C | 19 個同刻字品項，舒敏仍不在前八名；網頁展開完整搜尋後可見 | 刻字不唯一，需要更多特徵及人工核對 |

這項改善是找回已有的刻字資料，不是純 Computer Vision 準確率提升。`similarity: null` 表示沒有可用圖片特徵，不能視為已完成影像比較。相同刻字超過八筆時顯示完整筆數及展開搜尋入口，沒有為案例品項加特殊排名。證據保存在 `test-results/vision-imprint-before.json`、`vision-imprint-after.json`；瀏覽器實際操作 C 的 19 筆完整結果、SK KBT 的來源圖片與低分數說明。

## 2026-09-22：本機刻字 OCR 與輸入尺寸

先用三張原開發照片及六張既有實驗裁切圖，比較 Tesseract 的語言、頁面分割與灰階／二值化等 90 組設定，仍主要讀到尺規與背景，沒有採用這些前處理。接著比較專案已有的 PP-OCRv5 mobile：原照片可能讀到背景文字；六張 224×224 裁切图一律放大至 1280 時皆無文字。固定同一引擎，逐一比較 224、448、768、1280 輸入尺寸，共 24 組：原尺寸能讀到 Somin 的 C、K.B.T 的 SK／KBT，但 Fencaine 的 10 誤讀為 16；三張無刻字背面皆空白。未將實驗定位模型接入正式服務，也未將查詢圖加入參考索引。

改動前，從 3,878 個具有拉丁字母刻字且符合正式服務條件的品項，以 SHA-256(`pill-ocr-comparison-v1:${license}`) 排序固定抽取 32 張來源圖，排除上述三個開發品項。比較舊正式 Tesseract 流程與 Paddle 原尺寸／1280 上限：只計算「至少一行完整符合來源的一面刻字」，僅正規化 NFKC、大小寫與空白，不合併或修正字元。舊流程 0／32，新流程 5／32，沒有原先命中而退步的樣本。

這批是來源參考圖，不是獨立實拍；命中可能來自背景標示，100mg 也不代表已完整讀到另一面的 ST016。大部分樣本仍讀到尺規或漏字，所以不能將 5／32 宣傳為藥品辨識準確率。原始來源清單在 `test-results/pill-ocr-samples.json`；比較摘要在 `pill-ocr-benchmark-summary.json`；三張開發圖、不同尺寸及 Tesseract 比較在 `pill-ocr-paddle-development.json`、`pill-ocr-pilot.json`。比較時間 2026-09-22T14:16:07Z；之後正式 OCR 已更新，重跑開發頁的「原正式流程」會呼叫新版，不能再當作舊版基準。

正式採用現有 Paddle 讀取藥錠照片及保留小圖原尺寸；包裝照片的放大與 PDF 的 Tesseract 流程保留。增加同一面多行刻字勾選合併，保留重複行，不修正不確定數字。在隔離正式建置頁面實際上傳 K.B.T 裁切圖，讀到 SK／KBT，合併後找到許可證 007592 的克瀉寧，仍需點選確認。這改善的是文字輸入與本機檢索流程。

## 2026-09-22：文字位置對照及背景誤讀

正式藥錠模式讀取 496×496 的 Fencaine 完整開發照片時，輸出 10／20／30mm；保留 Paddle 回傳的文字位置後，照片上的橙框確認第一行 10 位於下方尺規，並非藥錠上的 10。位置百分比為 x 27.016、y 85.887、寬 13.911、高 6.653。這與前輪「包裝放大模式」或「224 裁切圖」的結果不同，不能混作同一測試設定。

照片 OCR 現可顯示各行讀取位置，重複刻字分別保留；勾選行顯示綠框，查看位置顯示橙框並將照片移到可見範圍。任何文字改動都停用舊框線對應，不把人工校正當成模型觀察。實際將上述文字依原照片人工校正為 FC／10 後，舊尺規框消失，合併查詢可找到芬康胃許可證 031990；仍屬人工確認文字後的查詢，不是照片自動辨識成功。

藥盒照片亦完成位置與既有兩筆許可證查詢驗證，PDF 保留原文字流程。預覽僅保留於瀏覽器，未寫入圖庫。證據見 `test-results/ocr-regions-ui-proof.json`；原尺寸完整照片仍漏讀藥錠小刻字，後續需另行比較區域及多尺度讀取，不能藉介面改善宣稱模型已解決此問題。

## 2026-09-22：保留原尺寸及小字補讀

沿用同一 PP-OCRv5 mobile 引擎，對三張開發原照片、六張既有裁切圖與上述固定 32 張來源圖片，逐張比較原尺寸（最長邊上限 1280）與放大至最長邊 1280，共 41 張、82 次讀取。模型只收到圖片；來源刻字僅在辨識後計算「至少一行完整符合來源的一面刻字」，沿用 NFKC、大小寫、空白正規化，不合併行或猜改文字。

| 固定 32 張來源圖 | 符合完整刻字的圖片數 |
| --- | --- |
| 原尺寸 | 5／32 |
| 僅放大 | 4／32 |
| 保留兩種讀法，任一符合 | 7／32 |

放大新增讀到 050769 的 C86、061048 的 GD，但原先可讀的 APO 變成 APG，MINCONLIN 與 S W 也失去完整符合。這不是可依信心分數自動挑選的可靠改善，因此正式介面保留兩組結果，由使用者對照位置；不把不同讀法合成模型原本未讀到的刻字。32 張熱啟動平均耗時為原尺寸約 1.22 秒、放大約 2.37 秒；各自最大約 1.98／3.35 秒，僅代表本機此次比較，不含首次引擎初始化。

Fencaine 的完整 496×496 開發照片，原尺寸為 `10／20／30mm`，放大為 `FC／10／10／20／30mm／0`。正式建置網頁實際切換後，第 2 行 10 的位置在藥錠（x 35.469%、y 56.25%），第 3 行 10 在尺規（x 28.203%、y 86.094%）；勾選 FC 與藥錠的 10 合併查詢，找到許可證 031990 一筆，確認清單仍為 0。這次未人工轉寫刻字，但仍由人選取同一面文字並確認候選。

其餘開發結果也保留：Somin 完整照片兩種讀法皆只有尺規；K.B.T 原圖含背景標示，放大未一致改善。Somin、K.B.T、Fencaine 的 224 裁切有刻字面原尺寸分別讀到 C、SK／KBT、FC／16，放大皆空白；三張無刻字面兩種讀法均空白。正式頁實測 Somin 裁切仍保留 C，沒有用空白補讀覆蓋。來源圖不是獨立實拍，部分符合可能來自背景或非唯一刻字；不能將 7／32 當成藥品身分辨識準確率。

## 2026-09-24：ePillID 配對照片與輕量距離學習

改用有「參考照／實拍照」配對的 [ePillID 作者公開資料](https://github.com/usuyama/ePillID-benchmark)，研究是否能學到比通用特徵更合適的距離。來源固定在 commit `6cb37099c0a3705ebd74afae79838817b453caad`；官方 release 壓縮檔 160,732,055 bytes，SHA-256 `b960b3b1f0ee145ae2be7cfe188de1feaba4286b5d2fb7388004d151ad7311ac`。README 明示資料與軟體供研究用途；程式 MIT 不直接等於影像或訓練後模型的商業散布授權。本次只保留於 `test-results/epillid-training/`，不匯入臺灣藥品身分、正式圖片索引或安裝包，也不執行下載的 notebook／pickle。

壓縮檔僅取出 32,997 張 JPG 與七份 CSV，逐檔檢查路徑、大小及雜湊。作者的 `all_labels.csv` 實際使用其中 13,532 筆影像：4,902 個藥品、9,804 張參考照與 3,728 張實拍照；960 個藥品具有兩者。888 組相同檔案內容跨越不同藥品編號，不能直接隨機分圖。依藥品編號、NDC 廠商／產品碼、檔案雜湊及解碼像素雜湊合併群組，正反面一起分組，並驗證五種鍵都不跨訓練／驗證／測試集。

使用 [torchvision 官方 ResNet18 ImageNet V1](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet18.html) 作固定編碼器，初始化權重完整 SHA-256 `f37072fd47e89c5e827621c5baffa7500819f7896bbacec160b1a16c560e07ec`；以 `weights_only=True` 載入。本機獨立 Python 環境為 torch 2.14.0+cpu、torchvision 0.29.0+cpu，Torch 限制兩個 CPU 執行緒，未改動應用程式相依套件。輸入採 RGB、白底等比例 224、ImageNet 正規化，輸出 512 維平均池化向量；保留完整藥錠而非套用分類模型預設中央裁切。

### 排名重算與未收錄品項的對照

完整批次執行期間，另外以唯讀特徵快取、獨立純量計算重算 72 張小圖庫的所有區域分數。十張查詢的正確品項排名、前八名順序及分數均一致；177 個區域向量通過維度、有限值與單位長度檢查。參考與查詢檔案、DEIM 及 DINOv2 權重亦核對雜湊。這證明該次算術與檔案一致，並不證明品項辨識正確。

再對每張查詢移除其正確品項的全部參考圖，保留其他品項與既定計算公式。十張查詢中，九張對其他品項的最高區域 cosine 超過 0.60，最高約 0.785；加入既定顏色／比例比較後仍有九張超過 0.60。其中四張純區域排名的第一、二名差距超過 0.04。**高相似分數或排名間距不能當成身分確認。** 0.60 在此只是拿現有整圖檢索門檻作對照，並非已校準的區域辨識門檻；正式服務原本就只回傳待核對候選，沒有因這次實驗改為自動確認。
